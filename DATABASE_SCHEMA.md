# PostgreSQL Database Schema - Leakage History

This document defines the PostgreSQL database for the Gas Leak Dashboard.

The dashboard needs **one table**: `leakage_history`. Each row is one leak event,
and the table is the source of the **Incident History** panel in the bottom-right
corner of the dashboard.

> **Status (current implementation):** The Node bridge (`Dashboard/server`) now
> uses PostgreSQL for incident history when `DATABASE_URL` is set. On startup it
> loads all incidents from `leakage_history`, resumes any open incident
> (`ended_at IS NULL`), and automatically inserts/updates/closes rows as new
> leaks are detected from the ESP32. The trend chart continues to use SQLite
> (`readings.db`) for continuous readings; only the Incident History panel is
> powered by PostgreSQL.

- One row = one leak incident (`warning` or `critical`).
- An incident starts when the sensor enters WARNING or DANGER and ends when it
  returns to SAFE.
- An open incident has `ended_at = NULL`; the dashboard shows the pulsing
  **Active** pill instead of a duration.
- Timestamps are stored as `TIMESTAMPTZ` and displayed in **IST**
  (`Asia/Kolkata`) by the frontend.

## Dashboard to Table Mapping

| Dashboard element | Table source |
|---|---|
| `#` | Row number generated by the list query, not stored |
| `Start (IST)` | `started_at` rendered in `Asia/Kolkata` |
| `Peak ADC` | `peak_adc` |
| `Severity` | `severity` (`warning` / `critical`) |
| `Duration` | `duration_ms`, derived from `started_at` and `ended_at` |
| `Active` pill | `resolved = false`, i.e. `ended_at IS NULL` |
| `N total` | `COUNT(*)` |
| `Critical (N)` / `Warn (N)` | counts filtered by `severity` |

The bridge's incident payload already maps directly to these columns:

| API / SSE field | Column |
|---|---|
| `startedAt` (epoch ms) | `started_at` (`TIMESTAMPTZ`) |
| `endedAt` (epoch ms or `null`) | `ended_at` (`TIMESTAMPTZ`) |
| `peakValue` | `peak_adc` |
| `severity` | `severity` |
| `resolved` | generated from `ended_at` |
| `durationMs` | generated from `started_at` / `ended_at` |

## Database Setup

Requires PostgreSQL 12 or newer (identity columns and stored generated
columns); PostgreSQL 14+ is recommended.

### Create Database and User

```sql
-- Connect as the postgres superuser
CREATE DATABASE gld_db;

CREATE USER gld_user WITH PASSWORD 'your_secure_password';
GRANT CONNECT ON DATABASE gld_db TO gld_user;
```

Connect to the new database and grant schema access:

```sql
\c gld_db

GRANT USAGE, CREATE ON SCHEMA public TO gld_user;
```

### Create the Table

```sql
CREATE TABLE leakage_history (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

    -- When the leak event started. The dashboard converts this to IST.
    started_at  TIMESTAMPTZ NOT NULL,

    -- NULL while the incident is still active.
    ended_at    TIMESTAMPTZ,

    -- Highest raw MQ-6 ADC reading seen during the incident (0-1023).
    peak_adc    SMALLINT NOT NULL CHECK (peak_adc BETWEEN 0 AND 1023),

    -- Worst state reached during the incident.
    severity    VARCHAR(10) NOT NULL CHECK (severity IN ('warning', 'critical')),

    -- "Active" pill vs. duration, derived so they can never disagree.
    resolved    BOOLEAN GENERATED ALWAYS AS (ended_at IS NOT NULL) STORED,
    duration_ms BIGINT GENERATED ALWAYS AS (
        CASE
            WHEN ended_at IS NULL THEN NULL
            ELSE (EXTRACT(EPOCH FROM (ended_at - started_at)) * 1000)::BIGINT
        END
    ) STORED,

    -- Bookkeeping, not shown in the dashboard.
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT leakage_history_ends_after_start
        CHECK (ended_at IS NULL OR ended_at >= started_at)
);
```

**Columns**

| Column | Type | Meaning |
|---|---|---|
| `id` | `BIGINT` | Auto-generated primary key. Use it as the incident id in the UI/SSE payload. |
| `started_at` | `TIMESTAMPTZ` | Start of the leak event. Rendered as **Start (IST)**. |
| `ended_at` | `TIMESTAMPTZ` | End of the leak event; `NULL` while active. |
| `peak_adc` | `SMALLINT` | Maximum raw ADC value during the event (**Peak ADC**). |
| `severity` | `VARCHAR(10)` | Worst severity reached: `warning` or `critical`. |
| `resolved` | `BOOLEAN` | Generated: `true` once `ended_at` is set. Drives **Duration** vs. **Active**. |
| `duration_ms` | `BIGINT` | Generated duration in milliseconds; `NULL` while active. |
| `created_at` | `TIMESTAMPTZ` | Row insert time. |
| `updated_at` | `TIMESTAMPTZ` | Last update time; set by the application on each write. |

### Indexes

```sql
-- Incident History list: newest first.
CREATE INDEX idx_leakage_history_started_at
    ON leakage_history (started_at DESC);

-- Critical / Warn filter tabs.
CREATE INDEX idx_leakage_history_severity
    ON leakage_history (severity, started_at DESC);

-- Fast lookup of the currently active incident.
CREATE INDEX idx_leakage_history_active
    ON leakage_history (started_at DESC)
    WHERE ended_at IS NULL;

-- At most one active incident at a time.
CREATE UNIQUE INDEX uq_leakage_history_single_active
    ON leakage_history ((ended_at IS NULL))
    WHERE ended_at IS NULL;
```

If more than one bridge will write to the same database, drop the last index;
the bridge process should then own incident tracking.

## Writing Leakage History

The bridge has two incident events (`incident-open` and `incident-close`) and
updates the open incident while readings continue.

### Open an Incident

Called on `incident-open`. Timestamps in the payload are epoch milliseconds, so
they are converted to `TIMESTAMPTZ`:

```sql
INSERT INTO leakage_history (started_at, peak_adc, severity)
VALUES (to_timestamp($1::double precision / 1000.0), $2, $3)
RETURNING id, started_at, ended_at, peak_adc, severity, resolved, duration_ms;
```

Keep the returned `id` in memory (or in the SSE payload) so later updates target
the same row.

### Update the Open Incident

Called on each reading while the incident is active:

```sql
UPDATE leakage_history
SET peak_adc   = GREATEST(peak_adc, $2),
    severity   = CASE
                     WHEN severity = 'critical' OR $3 = 'critical' THEN 'critical'
                     ELSE 'warning'
                 END,
    updated_at = now()
WHERE id = $1
  AND ended_at IS NULL;
```

### Close an Incident

Called on `incident-close`:

```sql
UPDATE leakage_history
SET ended_at   = to_timestamp($1::double precision / 1000.0),
    updated_at = now()
WHERE id = $2
  AND ended_at IS NULL
RETURNING id, started_at, ended_at, peak_adc, severity, resolved, duration_ms;
```

`resolved` and `duration_ms` update automatically because they are generated
columns - never write to them directly.

### Bridge Restart

If the bridge exits while an incident is active, decide what the open row means
before inserting a new one:

- If the leak is still active on the board, continue updating the existing row
  (select it with the query below and keep its `id`).
- If the event is over, close the orphan with the last known timestamp:

```sql
UPDATE leakage_history
SET ended_at   = COALESCE(ended_at, started_at),
    updated_at = now()
WHERE ended_at IS NULL;
```

The unique partial index will reject a second active row, which makes a missed
cleanup visible instead of silently splitting one leak into two incidents.

## Reading the Dashboard Data

### Incident History List

Returns exactly the columns the bottom-right table renders:

```sql
SELECT
    ROW_NUMBER() OVER (ORDER BY started_at DESC) AS row_number,
    started_at AT TIME ZONE 'Asia/Kolkata'       AS start_ist,
    peak_adc,
    severity,
    duration_ms,
    resolved
FROM leakage_history
ORDER BY started_at DESC
LIMIT 100;
```

`start_ist` is a `TIMESTAMP` (no time zone) already converted to IST, so the API
can send it as-is or serialize it back to an epoch millisecond value.

### Incident History Header Counts

```sql
SELECT
    COUNT(*)                                      AS total,
    COUNT(*) FILTER (WHERE severity = 'critical') AS critical,
    COUNT(*) FILTER (WHERE severity = 'warning')  AS warning,
    COUNT(*) FILTER (WHERE ended_at IS NULL)      AS active
FROM leakage_history;
```

### Filter Tabs

`All`, `Critical`, and `Warn` use the same list query with an optional filter:

```sql
-- Critical tab
SELECT
    ROW_NUMBER() OVER (ORDER BY started_at DESC) AS row_number,
    started_at AT TIME ZONE 'Asia/Kolkata'       AS start_ist,
    peak_adc,
    severity,
    duration_ms,
    resolved
FROM leakage_history
WHERE severity = $1          -- 'critical' or 'warning'
ORDER BY started_at DESC
LIMIT 100;
```

### Resume the Active Incident

On bridge start, find the row that was open when the process last stopped:

```sql
SELECT id, started_at, peak_adc, severity
FROM leakage_history
WHERE ended_at IS NULL
ORDER BY started_at DESC
LIMIT 1;
```

## Maintenance

Keep the history bounded by deleting old, resolved incidents. Active incidents
are never deleted:

```sql
DELETE FROM leakage_history
WHERE ended_at IS NOT NULL
  AND ended_at < now() - INTERVAL '90 days';
```

Run it periodically (cron, pg_cron, or a startup task), then vacuum if large
batches are deleted:

```sql
VACUUM ANALYZE leakage_history;
```

## Connection String

```text
postgresql://gld_user:your_secure_password@localhost:5432/gld_db
```

Use it from the Node bridge through an environment variable so the password is
not committed:

```powershell
$env:DATABASE_URL = "postgresql://gld_user:your_secure_password@localhost:5432/gld_db"
npm start
```

The dashboard server uses the `pg` package's connection pool with this URL.
The live trend chart keeps using its existing SQLite store/ring buffer (`readings.db`);
PostgreSQL only holds the leakage history that the Incident History panel reads.

### Bridge integration (implemented)

- Dependency added: `pg` in `Dashboard/server/package.json`
- Postgres client: `Dashboard/server/src/pgdb.js` (initializes table/indexes if missing, open/update/close/resume/load)
- Wired in `Dashboard/server/src/index.js`: loads incidents from PG on startup, resumes active incident if present, syncs `incident-open`/update/`incident-close` to PG, and keeps `session.incidents` in sync for the API/SSE
- Set `DATABASE_URL` in the environment before starting the bridge: `$env:DATABASE_URL = "postgresql://gld_user:your_secure_password@localhost:5432/gld_db"`
- Start: `cd Dashboard/server && npm start` (or `npm run demo` is not applicable; uses real serial). The dashboard (served by bridge at `:4310` or via Vite dev proxy) will display all rows from `leakage_history` in the bottom-right Incident History table.
